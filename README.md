## 课题 1：分流量为啥不准？——根因分析

### 遇到的问题

现实场景：

```
配置 50:50 的 AB 实验，跑出来 47:53，下一个实验又是 30:70
「为什么这么简单的事都做不好？」
```

### 问题的表现

```
5000 用户 / 10 组，10 次实验：
  实验 1: 490  520  510  480  505  495  500  502  498  500
  实验 2: 350  380  420  480  550  580  620  580  550  490  ← 偏差 27%
  实验 3: 480  510  495  510  500  495  510  500  500  500
```

最大组相对偏差波动范围：**±27%**（在 5000 量级）

### 根因分析

**数学下界**：实时分流的偏差下界 = `1.96 / √(N/G) × 100%`

| 累计样本量 N | 每组 | 偏差下界 (95%) |
|---|---|---|
| 5,000 | 500 | 8.77% |
| 50,000 | 5,000 | 2.77% |
| 500,000 | 50,000 | 0.88% |

**根因**：5000 用户下，纯随机分流就有 ~8% 偏差——不是算法 bug，是 √n 数学规律。

### 解决方案全景图

```
解决方案分三大类：
  1. 批量预分桶   → 偏差可控（不受 √n 限制）
  2. 实时校准     → 部分缓解（受 √n 限制，但能改进）
  3. 多层正交     → 解决流量复用（不解决偏差）
```

### 数据表现

实测 5 种常见实时分流方案（5000 用户 × 100 次抽样）：

| 方案 | 平均偏差 | < 1% 通过率 | 一致性 |
|---|---|---|---|
| 纯 hash | 8.05% | 0% | ✓ |
| 两次 hash 异或 | 7.82% | 0% | ✓ |
| 客户号 2 次哈希 | 7.91% | 0% | ✓ |
| 4-salt 众数投票 | 7.98% | 0% | ✓ |
| **校准路由 C1** | **0.20%** | **100%** | ✓ |

> **实验脚本**：[realtime_remedy.py](realtime_remedy.py)、[calibration.py](calibration.py)

### 一句话结论

5000 量级下，纯哈希不可能达到 1% 偏差。要么放大流量到 38 万（达到数学下界要求），要么换**批量预分桶**方案。

## 课题 2：能压到 1% 偏差吗？——数学下界扫描

### 遇到的问题

老板：「5000 用户分 10 组，偏差必须 < 1%。」

工程师：「5000 用户的偏差下界是 8.77%，压不到。」

老板：「那你为什么不能想个办法？」

### 问题的表现

在不同流量规模下实测实时分流偏差：

| 用户量 | 理论下界 | 实测平均偏差 | < 1% 通过率 |
|---|---|---|---|
| 500 | 27.72% | 24.64% | 0% |
| **5,000** | **8.77%** | **7.98%** | **0%** |
| 50,000 | 2.77% | 2.37% | 0% |
| 100,000 | 1.96% | 1.67% | 10% |
| 500,000 | 0.88% | — | — |

**关键发现**：5000 用户场景，**实测 0% 通过率**（100 次抽样全部超过 1%）。

### 根因分析

**为什么桶数不影响结果**？实测改变桶数 B（10 → 100000）：

| 桶数 B | 每桶人数 | 实测偏差 |
|---|---|---|
| 10 | 5000 | 2.51% |
| 100 | 500 | 2.59% |
| **1000** | **50** | **2.43%** |
| 10000 | 5 | 2.63% |
| 100000 | 0.5 | 2.56% |

**结论**：偏差只取决于**每组人数 N/G**，与桶数 B 无关。**加桶数没用**——这是 √n 数学规律。

### 解决方案

**满足 95% 置信度的最小累计样本量**：

| 目标偏差 | 每组最少 (N/G) | 10 组总流量 |
|---|---|---|
| 0.5% | 153,664 | 1,536,640 |
| 1.0% | 38,416 | 384,160 |
| 2.0% | 9,604 | 96,040 |
| 5.0% | 1,537 | 15,367 |

### 数据表现

实时分流 95% 置信度下的实测偏差：

```
N=5000 (10组): 实测 7.98% 平均偏差，0% < 1%
N=50000 (10组): 实测 2.37% 平均偏差
N=100000 (10组): 实测 1.67% 平均偏差，10% < 1%
```

### 一句话结论

**实时分流压到 1% 需要 38 万用户**（10 组总流量）。5000 量级下，实时分流根本达不到 1%。

## 课题 3：实时分流有哪些优化手段？——5 种方案实测对比

### 遇到的问题

「既然实时分流有 √n 下界，有没有什么办法能压低实际偏差？例如两次 hash、加 salt 等。」

### 5 种方案对比

| 方案 | 核心思路 | 实测偏差 | < 1% 通过率 | 一致性 |
|---|---|---|---|---|
| **R0** 纯 hash | `uid → bucket → group` | 8.05% | 0% | ✓ |
| **R2** 两次 hash 异或 | `hash1 ⊕ hash2 → group` | 7.82% | 0% | ✓ |
| **R3** 4-salt 众数投票 | 多次 hash 取众数 | 7.98% | 0% | ✓ |
| **客户号 2 次哈希**（字节风格） | 两次独立 hash | 7.91% | 0% | ✓ |
| **S2** 桶级微调 | 运行时重新映射桶-组 | 5.99% | 0% | ✓ |
| **C1** 校准路由 | 实时贪心均衡 | **0.20%** | **100%** | ✓ |

### 数据表现

100 次重复抽样结果（5000 用户 / 10 组）：

```
R0 纯 hash:        平均 8.05%  P95: 12.60%  < 1%: 0%
R2 两次 hash 异或: 平均 7.82%  P95: 11.61%  < 1%: 0%
客户号 2 次哈希:    平均 7.91%  P95: 11.62%  < 1%: 0%
R3 4-salt 众数投票: 平均 7.98%  P95: 11.62%  < 1%: 0%
S2 桶级微调:        平均 5.99%  P95: 8.51%   < 1%: 0%
C1 校准路由:        平均 0.20%  P95: 0.40%   < 1%: 100%
```

### 关键洞察

1. **加桶数没用**（受 √n 限制）
2. **两次 hash 不能消除 √n 下界**（独立波动叠加）
3. **客户号 2 次哈希的真实价值**：降低单次 hash 的系统性偏好，不是降低偏差
4. **校准路由 C1 是真正的"运行时突破"**：维护各组计数器，新用户倾向分到人少的组

### 一句话结论

实时分流优化手段中，**校准路由 C1 是唯一能在 5000 量级压到 0.2% 偏差的方案**。其他方案都是 8% 偏差（受 √n 限制）。

> **实验脚本**：[realtime_remedy.py](realtime_remedy.py)、[calibration.py](calibration.py)

## 课题 4：实时场景怎么做预分桶？——用户池预留机制

### 遇到的问题

「批量预分桶（蛇形分配）需要提前知道全量用户 ID，但用户是随时进入的。怎么办？」

### 解决方案：P1 用户池预留

**核心思想**：预分配 N 个虚拟槽位，真实用户来时"借"槽位。

```
启动时：                 运行时（O(1) 查询）：
virtual_users 50万        uid_u123 → 借 slot_1 → group_3
  ↓ 蛇形分配              uid_u456 → 借 slot_2 → group_7
slot_to_group 映射表
```

### 实现要点

```python
class UserPoolPreBucket:
    def __init__(self, capacity=50000, num_groups=10):
        # 启动时：预分桶 5 万虚拟槽位（蛇形分配）
        virtual_users = [f"v_{i:08d}" for i in range(capacity)]
        groups = assign_groups(virtual_users)  # 蛇形分配
        self.slot_to_group = {...}  # slot_id → group_id
    
    def route(self, user_id):
        if user_id in self.real_to_slot:
            return self.slot_to_group[self.real_to_slot[user_id]]
        # 新用户：按组均衡消耗槽位
        min_group = argmin(used_per_group)  # 找当前人数最少的组
        slot = next_unused_slot(min_group)
        self.real_to_slot[user_id] = slot
        return self.slot_to_group[slot]
```

**关键洞察**：实际用户 ID **完全不参与分组逻辑**，仅作为 `real_to_slot` 的 key 保证一致性。

### 数据表现（100 次抽样实测）

| 方案 | 用户量 | 平均偏差 | < 1% 通过率 | 一致性 |
|---|---|---|---|---|
| 纯实时 hash | 5,000 | 8.05% | 0% | ✓ |
| **P1 用户池预留** | **5,000** | **0.00%** | **100%** | ✓ |
| P2 动态扩容 | 5,000 | 0.00% | 100% | ✓ |

### 容量规划

| 容量 | 5000 用户使用率 | 评价 |
|---|---|---|
| 5,000 | 100% | ⚠️ 接近上限 |
| 10,000 | 50% | ✓ 安全 |
| 50,000 | 10% | ✓ 推荐 |
| 100,000 | 5% | ✓ 高枕无忧 |

### 一句话结论

**用户池预留（P1）是 5000 量级下唯一能稳定达到 0% 偏差的方案**。预分桶表 + 按组轮转消耗槽位 = 0% 偏差 + O(1) 查询 + 100% 一致性。

> **实验脚本**：[realtime_prebucket.py](realtime_prebucket.py)

## 课题 5：多团队并发怎么解？——多层正交实验

### 遇到的问题

「推荐团队要做实验（占 50%），搜索团队也要做实验（占 50%），UI 团队也要（占 30%）——加起来超过 100%，流量不够分怎么办？」

### 解决方案：多层正交

**核心思想**：每层独立分流，层间流量正交复用。

```
用户 u123:
  Layer 1 (推荐实验):  hash(u123, "rec") → group A
  Layer 2 (搜索实验):  hash(u123, "sch") → group C  
  Layer 3 (UI 实验):    hash(u123, "ui")  → group X

数学保证: N(A∩C) = N(A) × N(C) / N_total
```

### 数据表现（5000 用户 × 50 次抽样）

| 指标 | 实测值 | 判定 |
|---|---|---|
| 正交通过率（p > 0.05） | **100%** | ✓ 完美正交 |
| 卡方 p-value 中位数 | 0.48 | 远大于 0.05 |
| 列联表最大偏差 | 1.13% | 与组数 2 的泊松波动一致 |
| 三层 8 组合分布平衡率 | 0.89 | 接近理想 1.0 |

**单层偏差**（实时，每层 2 组）：

| 层 | 平均偏差 | P95 | < 1% 通过率 |
|---|---|---|---|
| L1 推荐 | 1.24% | 2.89% | 52% |
| L2 搜索 | 0.89% | 2.11% | 60% |
| L3 UI | 1.35% | 2.55% | 34% |

### 关键洞察

1. **每层独立 salt 哈希**：保证层间完全独立（卡方检验 100% 通过）
2. **100% 流量可被多个实验同时使用**：3 个团队各占一层
3. **不解决单层偏差问题**：每层仍然是 √n 下界

### 一句话结论

**多层正交解决流量复用问题，不解决单层偏差**。每层仍需用 P1 或蛇形分配来控制偏差。

> **实验脚本**：[orthogonal_layers.py](orthogonal_layers.py)

## 课题 6：批量 vs 实时到底有什么不同？——架构对比

### 核心差异表

| 维度 | 批量预分桶（蛇形/P1） | 实时分流（纯 hash） |
|---|---|---|
| **算法复杂度** | O(N log N)（含排序） | O(1)（哈希） |
| **启动开销** | 高（需全量计算） | 无 |
| **单次查询** | O(1)（查表） | O(1)（哈希） |
| **内存占用** | O(N)（存全量映射） | O(1)（无状态） |
| **偏差控制** | **不受 √n 限制** | **受 √n 限制** |
| **5K/10组 偏差** | **0% - 0.51%** | **8%** |
| **1% 偏差所需流量** | 任意（5K 也行） | 38 万 |
| **一致性** | ✓ 强 | ✓ 强 |
| **新用户处理** | 首次落表 | 直接 hash |
| **工程复杂度** | 中（需预计算） | 低（直接调用） |

### 数据表现

| 方案 | 用户量 | 平均偏差 | < 1% 通过率 |
|---|---|---|---|
| **批量蛇形分配** | 5,000 | 0.51% | 96% |
| **批量蛇形分配** | 10,000 | 0.32% | 100% |
| **批量蛇形分配** | 100,000 | 0.06% | 100% |
| **用户池预留 P1** | 5,000 | **0.00%** | **100%** |
| 纯实时 hash | 5,000 | 8.05% | 0% |
| 校准路由 C1 | 5,000 | 0.20% | 100% |

### 关键洞察

- 批量方案在 **5K-100K** 流量下都能达到 < 1% 偏差
- 实时方案要达到 < 1% 偏差需要 **38 万用户**（√n 改善）
- **P1 用户池预留 = 批量 + 实时的最佳组合**（预分桶的准确性 + 实时进入的灵活性）

### 一句话结论

**5000 量级下，批量预分桶（P1 用户池预留或蛇形分配）完胜实时分流**。批量方案偏差 0-0.51%，实时方案偏差 8%。

## 课题 7：偏差稳了就能检出效果吗？——MDE 评估

### 遇到的问题

「5000 用户分 10 组，偏差 < 1%，分流也通过了卡方检验——但为什么跑了 2 周还是看不出 A 组比 B 组好？」

### MDE（最小可检测效果）公式

$$MDE = \frac{(z_{\alpha/2} + z_{\beta}) \sqrt{2 p_0 (1-p_0)}}{\sqrt{n}}$$

### 数据表现

| 指标 | 数值 |
|---|---|
| 每组样本量 | 501 |
| 基线转化率 | 5% |
| **95% 置信 / 80% 功效下 MDE** | **24.42%** |
| 含义 | 小于 24.42% 的效果差异无法可靠检出 |

**结论**：5000 用户 / 10 组 → 每组 500 人 → 即使偏差 0%，也**检测不出 24% 以下的效果提升**。

### 与偏差控制的关系

```
误区："偏差 < 1%" ≠ "能检出效果"

正确理解：
  偏差控制：解决"分组是否均匀"
  效果检出：解决"样本量是否足够"

两者必须同时满足，否则：
  偏差不均 → 分组不公平 → 结论不可信
  样本不足 → 真有效果也检不出 → 浪费实验时间
```

### 一句话结论

**偏差稳了只是必要条件，还要 MDE 达标**。5000 用户下，即使分组完美，要检出 24% 以下的效果提升也不够。

## 课题 8：工程上怎么落地？——工业部署方案

### 遇到的问题

「方案都分析了，工程上到底怎么部署？Redis 还是 MySQL？单机还是分布式？容量怎么规划？」

### 推荐方案：P1 用户池预留 + Redis

```
┌─────────────────────────────────────┐
│      启动时（一次性）                 │
│  1. 预分桶 5 万虚拟用户槽位           │
│  2. 蛇形分配 → 生成 slot_to_group 映射│
│  3. 加载到 Redis（持久化）            │
└─────────────────────────────────────┘
            ↓
┌─────────────────────────────────────┐
│      运行时（O(1) 查询）            │
│  GET /exp/route?uid=u_xxx            │
│    → Redis: HGET exp:001 real_to_slot│
│    → 若有：返回槽位的 group           │
│    → 若无：LPOP unused_slots → 绑定   │
│    → 返回新槽位的 group              │
└─────────────────────────────────────┘
```

### 场景化推荐

| 场景 | 推荐方案 | 预期偏差 | 工程成本 |
|---|---|---|---|
| **小流量 (< 1万)，单实验** | **P1 用户池预留** | **0%** | **低** |
| 中流量 (1-10万)，单实验 | 批量蛇形 + 静态查表 | < 1% | 中 |
| 大流量 (> 10万)，单实验 | 纯实时 + 大流量 | < 1% | 极低 |
| 多团队并发 | 多层正交 + P1 | < 1% | 高 |
| 实验规模不可预估 | P2 动态扩容 | < 1% | 中 |
| 接受 5% 偏差即可 | C1 校准路由 | ~2% | 中 |
| 接受 8% 偏差 | 纯实时 | ~8% | 极低 |

### 部署关键点

1. **预计算时机**：实验启动前完成 P1 初始化（< 1 秒）
2. **容量规划**：预留 5 倍预估用户量（5K 用户预留 25K 槽位）
3. **持久化**：Redis 保存 `real_to_slot` 映射（保证重启后一致性）
4. **扩容**：当 utilization > 80% 时触发异步扩容
5. **监控**：实时监控各组人数偏差、SRM 检验结果

### 关键代码

```python
import mmh3
from ab_split_validator import assign_groups

class ProductionRouter:
    def __init__(self, capacity=50000, num_groups=10):
        virtual_users = [f"v_{i:08d}" for i in range(capacity)]
        groups = assign_groups(virtual_users, num_buckets=min(capacity, 1000),
                               num_groups=num_groups, salt="exp_001")
        self.slot_to_group = {
            int(v.split("_")[1]): gid
            for gid, v_users in groups.items()
            for v in v_users
        }
        self.unused_slots = list(range(capacity))
        self.real_to_slot = {}
        self.used_per_group = {g: 0 for g in range(num_groups)}
    
    def route(self, user_id):
        if user_id in self.real_to_slot:
            return self.slot_to_group[self.real_to_slot[user_id]]
        
        # 按组均衡消耗
        min_group = min(range(10), key=lambda g: self.used_per_group[g])
        slots = [s for s, g in self.slot_to_group.items() if g == min_group]
        for slot in slots:
            if slot not in self.real_to_slot.values():
                self.real_to_slot[user_id] = slot
                self.used_per_group[min_group] += 1
                return self.slot_to_group[slot]
```

### 一句话结论

**工业部署推荐：P1 用户池预留 + Redis**。启动时预分桶，运行时 O(1) 查表，0% 偏差，100% 一致性。

## 核心结论

| 流量规模 | 推荐方案 | 实测偏差 |
|---|---|---|
| < 1 万（5000 量级） | **P1 用户池预留** | **0.00%** |
| 1-10 万 | 批量蛇形 + Redis 查表 | < 1% |
| 10 万以上 | 纯实时 + 大流量自然收敛 | < 1% |
| 多团队并发 | 多层正交 + P1 | < 1% |

**一句话总结**：5000 用户 / 10 组下，纯实时分流数学上不可能达到 1% 偏差（实测 8%）。**用户池预留（P1）+ Redis 部署**是工业级最佳方案，实测 0% 偏差 + 100% 一致性 + O(1) 查询。
