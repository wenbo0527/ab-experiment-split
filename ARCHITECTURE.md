## 数据采集假设

本项目的代码库**假设输入数据满足以下条件**：

```
1. 每个用户有唯一 user_id
2. 实验组 / 对照组有明确标记（assigned: 0/1）
3. 有实验前数据（pre 期），可用于 CUPED / DID
4. 有实验后数据（post 期），是真实 Y
5. 有用户级特征（age / income / credit_score 等）
```

如果你的数据不满足上述条件（比如某些实验没有 pre 期），代码需要相应调整。

## 性能与可扩展性

```
脚本运行时长（实测）：
  - 流量分配脚本:        < 5 秒
  - 100 次蒙特卡洛:       5-30 秒
  - 200 次蒙特卡洛:       30-90 秒
  - 1000 次 A/A:          60+ 秒

内存占用：
  - 单脚本运行:           < 100 MB
  - Kaggle 数据全集:      ~ 1.5 GB（包含原始 CSV）

并行化：
  - 蒙特卡洛循环可改为多进程加速（n_jobs 参数）
  - 当前版本未启用，n_trials 较小无需并行
```

## 安全与合规

```
本项目：
  ✓ 不存储任何业务数据（除 Kaggle 公开数据）
  ✓ 不向外部网络发送数据
  ✓ 不修改任何系统配置
  ✓ 所有操作可追溯（git history）

生产部署时需要补充：
  □ 用户隐私脱敏（GDPR / 个保法）
  □ 实验结果权限控制（谁能看哪个实验）
  □ 审计日志（谁何时运行了哪个实验）
  □ 数据访问授权（哪个团队用哪个数据集）
```

## 常见架构问题

### Q: 这个项目能直接上生产吗？

不能。它是一个**原理 + 验证 + 参考实现**的项目，要上生产需要补：
- 数据采集层（埋点 / 上报）
- 实时分流服务（Redis 路由）
- 监控告警（Prometheus / AlertManager）
- 用户权限系统
- 合规报备（金融场景）

### Q: 为什么没有 web 界面？

这个项目的目标读者是**想做 AB 实验的工程团队**，不需要 web 界面。
他们的下一步是根据这份参考实现，集成到自己的产品中。

### Q: 数据从哪里来？

代码层面只演示了**算法和数据结构**。真实部署需要：
- 业务方提供埋点日志
- 数据团队把日志转成"用户级数据"
- 然后才能调用本项目的算法
